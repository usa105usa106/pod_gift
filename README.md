# Gift Hunter v0042

Gift Hunter v0042 запускает от одного до шести независимых Telegram-стрелков из одного репозитория и одного Docker-образа.

- **Hunter 1:** независимый локальный залп `1–50`.
- **Hunter 2–6:** независимый локальный залп `1–50` у каждого аккаунта.
- Первый Hunter, который видит номер перед выстрелом, создаёт все задачи своего залпа и сразу отправляет остальным локальный UDP-сигнал внутри Docker-сети; результатов своего залпа он не ждёт.
- FIRE подписан и привязан к конкретной коллекции, generation и номеру выстрела. Сигнал от другой коллекции с тем же номером будет проигнорирован.
- Если локальный платёжный план первого обнаружившего неисправен, FIRE всё равно передаётся остальным стрелкам, чтобы они не ждали собственного более позднего обнаружения.
- Каждый Hunter продолжает самостоятельно сканировать Telegram, поэтому локальное обнаружение остаётся резервным путём при недоступном UDP.

> Номер «Выстрел» — первый ожидаемый номер после триггера. Например, при выстреле `4439` триггером служит появление `4438`. Telegram не гарантирует, что результат конкретного запроса получит именно `4439`.

## Развёртывание в Coolify

Создайте в Coolify один ресурс типа **Docker Compose** из этого репозитория. Compose заранее описывает шесть сервисов:

```text
hunter-1 — основной бот
hunter-2 — спит до выдачи токена
hunter-3 — спит до выдачи токена
hunter-4 — спит до выдачи токена
hunter-5 — спит до выдачи токена
hunter-6 — спит до выдачи токена
```

В Environment Variables Coolify при первом запуске нужны только:

```env
BOT_TOKEN=токен BotFather для Hunter 1
SETUP_PIN=ваш закрытый PIN
```

`FIRE_SECRET` вручную задавать не нужно. Hunter 1 при первом запуске автоматически создаёт 256-битный случайный ключ и сохраняет его в общем persistent provision-volume как `/provision/fire-secret.txt`. При redeploy тот же ключ используется повторно; параллельный запуск старого и нового контейнера защищён файловой блокировкой, а частично записанный файл восстанавливается автоматически; Hunter 2–6 ждут его появления и читают только сохранённое значение. Необязательная переменная `FIRE_SECRET` оставлена только как совместимый ручной override.

`FIRE_PORT` наружу публиковать не нужно. Все шесть сервисов находятся в одной Compose-сети и обращаются друг к другу по именам `hunter-1` … `hunter-6`.

После Deploy:

1. Откройте Hunter 1 и нажмите `/start`.
2. Введите `SETUP_PIN`.
3. Укажите количество стрелков от 1 до 6.
4. Для каждого дополнительного Hunter отправьте отдельный BotFather-токен. Сообщение с токеном удаляется сразу после чтения.
5. Откройте каждого активированного бота, нажмите `/start` и настройте его отдельно.

Hunter 2–6 не создаются динамически и не получают доступ к Docker или API Coolify. Их контейнеры уже описаны в Compose, но до появления токена работают как лёгкие bootstrap-процессы без Bot API, MTProto и сканирования. Общая конфигурация и lifecycle лежат в одном provision-volume, а токены Hunter 2–6 — в пяти отдельных token-volumes; каждый вторичный контейнер монтирует только собственный токен.

## Изменение количества стрелков после настройки

У Hunter 1 есть отдельная кнопка:

```text
👥 Количество стрелков: 1
```

Она показывается только в Hunter 1. Redeploy, удаление volumes и повторная авторизация Hunter 1 не требуются. При нажатии Hunter 1 останавливает собственный сканер и стресс-тест, выключает LIVE, затем просит новое число `1–6`. Уже сохранённые токены Hunter 2–6 используются повторно; бот запрашивает только отсутствующие.

При увеличении состава заранее созданные bootstrap-контейнеры принимают новую конфигурацию только после двух одинаковых корректных чтений и просыпаются при наличии своего сохранённого токена. При уменьшении состава Hunter 1 немедленно отправляет подписанное UDP-уведомление всем прежним участникам: они выключают LIVE, останавливают сканер/стресс-тест, очищают подготовленные платежи и ждут подтверждённую конфигурацию. Засыпание разрешено только после двух одинаковых корректных чтений новой `generation`; ошибка чтения или повреждённый JSON не считаются командой сна.

После изменения состава Hunter 1 один раз ждёт подтверждения активных и отключённых контейнеров, затем выполняет ручной UDP-опрос и показывает результат. Постоянного фонового Ping для этого нет. Токены и MTProto-volumes исключённых Hunter не удаляются: при последующем увеличении состава они используются повторно.

## MTProto-авторизация

Каждый стрелок использует отдельный пользовательский Telegram-аккаунт и отдельный volume. Найдите реальные имена контейнеров Coolify:

```bash
docker ps --format '{{.Names}}'
```

Затем авторизуйте аккаунты по очереди:

```bash
docker exec -it <контейнер-hunter-1> python /app/main.py auth
docker exec -it <контейнер-hunter-2> python /app/main.py auth
```

Повторите для всех выбранных стрелков. Код Telegram и облачный пароль 2FA вводятся только в терминале. Не храните пароль в Environment Variables.

Не удаляйте volumes и не используйте `docker compose down -v`: в отдельных volumes хранятся MTProto-сессии и настройки каждого Hunter.

## Обычный порядок настройки

Во всех контейнерах одинаковый интерфейс и одинаковая последовательность:

1. Авторизация.
2. Выбор канала и подарка.
3. Номер выстрела.
4. Размер залпа.
5. Включение LIVE.
6. Кнопка «Запустить».
7. Появление полной карточки сканера.

Hunter 1 всегда может выбрать залп `1–50`. Hunter 2–6 каждый независимо может выбрать залп `1–50`. Значения не выравниваются Hunter 1 и не сбрасываются при изменении количества стрелков.

В обычных режимах `/pachka off` для каждого платежа нужен отдельный выбранный неулучшенный подарок и отдельная заранее подготовленная платёжная форма. `PACHKA ON` — специальный экспериментальный режим для **ровно двух** выбранных подарков: Gift A получает одну форму, а пять дополнительных разных форм заранее привязаны к тому же Gift B. Ни одна из этих шести форм не может переключиться на третий `saved_id`.

### Платёжные формы v0042 и длительная работа

Telegram Stars-форма действует 10 минут. v0042 не держит одну форму месяцами: во время активного LIVE отдельный фоновый worker постоянно обновляет формы небольшими партиями. Дальше чем за 50 номеров до следующей цели каждая форма обновляется после 300 секунд (5 минут), а на расстоянии 50 номеров и ближе — после 120 секунд (2 минуты). При первом входе в зону 50 номеров весь FAST-комплект дополнительно обновляется принудительно. Worker после этого **не замораживается** и продолжает менять `form_id`, сколько бы ни длилось ожидание возле цели. FAST по-прежнему отказывается отправлять форму старше 480 секунд; при Telegram/FloodWait/сетевой ошибке refresh повторяется, а устаревшая форма fail-closed не отправляется.

В карточке сканера строка `FAST-формы` показывает возраст старшей формы и число успешных обновлений. Если refresh падает, рядом выводится последняя ошибка, поэтому зависший lifecycle видно без выгрузки полного лога.

Для каждого платного экземпляра проверяется связка `saved_id → invoice.stargift.saved_id → form_id → request.form_id`. Совпадение `form_id` у двух разных подарков блокирует весь FAST-залп до оплаты.

### FAST-залп v0042: PACHKA + сохранённые NEXT-TICK/RESPONSE-CHAIN

По умолчанию `/pachka on`. В этом режиме LIVE разрешается только при залпе `2` и ровно двух выбранных экземплярах. До выстрела формируется фиксированный комплект из **6 разных payment forms**: `A@0`, затем `B@20/35/50/75/100 мс`. Все пять B-форм привязаны к одному и тому же второму `saved_id`; pair lock, invoice binding, request binding и уникальность всех `form_id` проверяются до первого financial RPC.

Смещения 20/35/50/75/100 мс считаются от фактического queue первого запроса в `client._sender`, а не от момента обнаружения триггера. Последующие запросы заранее планируются по абсолютным deadline и **не ждут** ответов предыдущих. После отправки лог сохраняет planned offset, фактический queue offset, schedule error и response offset для каждой из шести форм.

`/pachka off` отключает экспериментальную пачку и возвращает без изменений оба режима v0041. `/otvet off` — NEXT-TICK: первый payment ставится в уже подключённый sender, затем один `await asyncio.sleep(0)` и следующий payment без ожидания Telegram. `/otvet on` — RESPONSE-CHAIN: следующий заранее подготовленный payment ставится сразу после raw RPC future предыдущего, без NFT-проверки, UI, логирования, дискового I/O или `invokeAfterMsg` между ответом и следующим queue. Пока PACHKA включена, `/otvet` хранится как fallback и начинает действовать после `/pachka off`.

Persistent `payment-submit-guard` в v0042 **полностью отсутствует в firing path**. Перед первым выстрелом нет guard-файла, `fsync` или другой durable-операции. Старый `payment-submit-guard.json` остаётся только legacy-мусором для очистки полным Reset. Финансовые requests не получают автоматического response-driven retry.

Активный сканер по-прежнему пишет `scanner-resume.json` и watchdog перед hard-exit пишет stack dump всех Python-потоков в `gift-hunter-v0042-watchdog.log`. Ручная остановка, завершённый залп и полный Reset удаляют resume-marker.

Кнопка `🗑 Сброс` остаётся аварийным **полным рабочим сбросом**: очищает канал, выбранные подарки, цели, LIVE, slug-map, payment hold, cooldown/rate-limit, resume-marker и временные диагностические файлы. Сохраняются авторизация владельца, `TG_API_ID/TG_API_HASH/phone`, MTProto `*.session` и исторические логи/payment-audit. После Reset рабочие режимы возвращаются к `/pachka on` и `/otvet off`.

Отдельный структурированный журнал `gift-hunter-v0042-payment-audit.jsonl` хранит подготовку, обновление, ошибки форм, binding-поля и результат каждого FAST-запроса. `/log_full` выгружает из него и из основного журнала только события за последние 24 часа. Если итоговый ZIP превышает безопасный предел 49 MB, он автоматически разбивается на несколько самостоятельных ZIP-частей. Только после успешной отправки всех частей локальная история логов старше 24 часов удаляется; при ошибке отправки файлы остаются на VPS. Между выгрузками основной лог и payment-audit продолжают использовать ротацию `25 MB × 13 файлов` каждый.

## Готовность стрелков

После успешного запуска с включённым LIVE каждый дополнительный бот один раз сообщает:

```text
🟢 HUNTER 2 ПОЛНОСТЬЮ ГОТОВ
BOT:       ✅
MTProto:   ✅
Подарок:   ✅
Выстрел:   ✅ #4439
План:      ✅
Сигнал:    ✅ UDP
LIVE:      ✅
```

Hunter 1 показывает общую карточку выбранного состава. Служебный статус передаётся локально не чаще одного раза в 60 секунд и при изменении готовности. Telegram-карточка Hunter 1 не редактируется чаще раза в минуту.

## Ручной Ping стрелков

Существующая кнопка `📡 Ping` сохранена. Автоматического фонового Ping нет.

Во всех Hunter обычный PONG показывает состояние бота, MTProto, сканера, текущее потребление RAM, доступный лимит контейнера, время работы процесса и обработку команды. Поля «Карточка», «Стресс-тест», «Проверок сканера», «Последний цикл» и «Текущие номера» из PONG удалены как дубли основной карточки.

В Hunter 1 тот же Ping дополнительно выполняет немедленный HMAC-подписанный UDP-опрос всего выбранного состава, включая собственный UDP-обработчик Hunter 1:

```text
👥 Стрелки:
Hunter 1 — 🟢 UDP 0.11 мс (локальный)
Hunter 2 — 🟢 UDP 0.42 мс
Hunter 3 — 🔴 нет ответа

Ответили: 2/3
```

RTT измеряет Hunter 1 через монотонные часы; синхронизация времени контейнеров не нужна. Опрос выполняется только после ручного нажатия и не меняет LIVE, не запускает сканер и не выполняет MTProto-запросы у участников.

## Защита от ложного сна и зависания

Каждый корректный `cluster.json` содержит возрастающую `generation`. Активный Hunter хранит последнюю принятую конфигурацию в памяти. При временной ошибке диска, отсутствующем или повреждённом файле он продолжает использовать последнее корректное значение и пишет `cluster_config_invalid_ignored`; значение `1` автоматически не подставляется.

Новая конфигурация у Hunter 2–6 применяется только после двух последовательных одинаковых чтений. Подписанное UDP-уведомление используется для немедленного безопасного разоружения, но само по себе никогда не переводит процесс в сон. Финальное отключение происходит только после подтверждения файла, после чего lifecycle-файл получает состояние `sleeping` и `deactivation_ack`.

В каждом активном процессе работает независимый watchdog-поток. Если asyncio-цикл не двигается дольше `WATCHDOG_STALL_SECONDS`, watchdog пишет stack dump всех Python-потоков, фиксирует причину в lifecycle/общем журнале и завершает процесс; `restart: unless-stopped` запускает контейнер заново. Если перед stall сканер был активен, `scanner-resume.json` позволяет v0042 автоматически пересобрать план/формы и продолжить работу. Persistent payment guard в v0042 не используется: после аварии бот не выполняет автоматический повтор Stars-платежа; уже обработанные неоднозначные результаты по-прежнему переводятся в payment hold. Docker-контейнер, остановленный вручную, watchdog запустить не может.

## Карточка сканера

Формат рабочей карточки сохранён. В ней остаются:

- состояние сканера и LIVE;
- MTProto и выбранный канал;
- число проверок;
- последний цикл, адаптивный период и фактический шаг в миллисекундах;
- FloodWait, cooldown и uptime;
- возраст старшей FAST-формы и число успешных refresh;
- текущий номер и номер **выстрела**.

Карточка отправляется без прикреплённой клавиатуры. Управляющие кнопки находятся в отдельном сообщении.

До тихого режима карточка обновляется:

- сразу при изменении текущего номера;
- раз в 60 секунд, если номер не изменился.

## Тихий режим

По умолчанию тихий режим начинается за 10 номеров до выстрела:

```env
FAST_QUIET_DISTANCE=10
```

Отдельно от тихого режима встроена зона обслуживания FAST-форм: при расстоянии
`50` номеров до следующей цели LIVE один раз принудительно обновляет весь локальный
FAST-боекомплект и вооружает его. После этого фоновый refresh **не останавливается**:
внутри этой зоны каждая форма обслуживается по 2-минутному циклу, а дальше 50
номеров — по 5-минутному. Эти значения встроены в релиз и не требуют переноса или
переименования переменных в Coolify. Если полный комплект временно обновить не
удалось, сканер остаётся fail-closed, но повторяет попытку вооружения после паузы и
не делает refresh непосредственно после точного `target-1` триггера.

При выстреле `4439` он включается при текущем номере `4429`. В карточку добавляется только верхняя строка:

```text
🔕 Бот в тихом режиме
```

Остальной текст карточки не меняется. Автоматические редактирования прекращаются, но сканирование, миллисекундные измерения, UDP и подготовленные платежи продолжают работать.

Кнопка `♻️ Обновить карточку` присылает новую полную карточку из данных в RAM. Она не выполняет дополнительный MTProto-запрос, не пересобирает план и не прикрепляет клавиатуру.


## Проверка номеров всех коллекций

Кнопка `🔢 Проверить номера` показывает название, последний выпущенный номер и максимальный общий выпуск:

```text
Durov’s Glasses — 3441 — 4982
```

Если до ближайшего повторяющегося красивого номера из 4, 5 или 6 одинаковых цифр остаётся не более 100 выпусков, текущий номер выделяется жирным. Это работает для всех цифр `1–9`, например:

```text
Durov’s Glasses — 4344 — 4982       # до 4444 осталось 100
Chill Flame — 444350 — 482271       # до 444444 осталось 94
```

Каждая такая проверка записывает:

- итоговые события в обычный файл лога;
- полный снимок `catalog-numbers-latest.json` с `issued`, `total`, slug, ошибкой, ближайшим красивым номером и расстоянием до него.

Файл автоматически попадает в архив `/log_full`, поэтому после ошибки можно увидеть не только текст сообщения, но и исходные данные по каждой коллекции.

## Логи и `/log_full`

Обычный файл каждого Hunter остаётся в его собственном data-volume. В нём фиксируются запуск сканера и фактический режим:

```text
scanner_started shooter_id=1 mode=sniper volley=1 ...
scanner_started shooter_id=1 mode=volley volley=12 ...
```

После завершения первого и единственного FAST-submit записывается итог залпа:

```text
fast_volley_completed shooter_id=2 source=udp campaign_id=... predecessor=4443 target=4444
volley=1 udp_peers_sent=0 first_send_start_ms=... task_launch_ms=... outcomes=[...]
```

`campaign_id` связывает FIRE с конкретной коллекцией. Для каждого платежа отдельно сохраняется фактический момент входа в MTProto-вызов (`send_start_ms`), фактический номер и ошибка. Если локальный план первого обнаружившего оказался неисправен, пишется `fast_local_preflight_failed_relayed` с числом получивших FIRE peers.

Для каждого подарка в `outcomes` сохраняются `saved_id`, статус, фактический номер и безопасно обрезанное описание ошибки. При локальном обнаружении `source=local`; у участника, получившего общий сигнал, `source=udp`. Прикладного повтора платежа нет.

Hunter 1 также логирует весь процесс подключения дополнительных BotFather-ботов:

- получение сообщения и результат его удаления;
- отклонение дубликата;
- результат проверки токена;
- сохранение файла токена и его права `0600`;
- завершение настройки выбранного состава.

Значения токенов, автоматически созданный `FIRE_SECRET`, пароли и `api_hash` в логи и `/log_full` не записываются. Вторичные токены находятся в отдельных volumes, а общий provision-volume содержит файл `cluster-events.jsonl`; в него все контейнеры добавляют критические события bootstrap, готовности, запуска сканера и завершения снайперского/залпового выстрела. Секретоподобные поля дополнительно редактируются перед записью.

Команда `/log_full` формирует диагностический архив **только за последние 24 часа**:

- строки обычных и ротированных логов текущего Hunter за это окно;
- строки `payment-audit` за это окно;
- `stress-tests.jsonl` и общий `cluster-events.jsonl` только за это окно;
- актуальные снимки `diagnostics.json`, `catalog-numbers-latest.json`, stress/rate-limit;
- актуальные `cluster.json`, `cluster-generation.json` и lifecycle-файлы Hunter.

Если один ZIP получился больше 49 MB, `/log_full` автоматически создаёт и отправляет несколько независимых ZIP-файлов вида `part01-ofNN`. После успешной отправки **всех** частей на VPS удаляются только записи старше 24 часов; текущие и свежие ротированные записи остаются. Если хотя бы одна часть не отправилась, очистка не выполняется. Временные ZIP-файлы после команды удаляются с VPS.

Поэтому архив Hunter 1 показывает ключевой межконтейнерный путь последних 24 часов, не накапливая месяцы старой диагностики после её выгрузки. Низкоуровневый процессный лог конкретного участника по-прежнему выгружается командой `/log_full` в его собственном боте.

## Ограничения

Gift Hunter не резервирует номер и не управляет очередью Telegram. Полученный номер зависит от серверной обработки, конкурирующих запросов, маршрута и момента появления свежего состояния.

В v0042 нет response-driven автоматического повторного submit финансового request. При `/pachka on` шесть **заранее подготовленных** разных forms отправляются по фиксированному расписанию `0/20/35/50/75/100 мс` и навсегда привязаны только к двум выбранным `saved_id`; поздние B-запросы не отменяются по раннему RPC-ответу, потому что цель режима — измерить/поймать серверное окно готовности до полного ответа. При `/pachka off` доступны неизменённые NEXT-TICK и RESPONSE-CHAIN через `/otvet off/on`. Фактические интервалы измеряются в payment-audit. Для охоты на Durov’s Glasses #4444 в каждом участнике задаётся выстрел `4444`; точным триггером будет свежий номер `4443`.
